# weekly-review

inbox の日次まとめノートから **「後で読む」** とマークされた記事だけを抽出し、深読みして整理する。

## Inkdrop MCP の使用方法と注意点

スキル開始前に、各CLIにおける Inkdrop MCP の呼び出し方針を確認すること。
特に 1Password (`op run`) による認証が走るため、不要なタイミングでの認証ポップアップを防ぐ必要がある。

- **Claude Code**: `~/dotfiles/` から `claude` を起動する（`~/dotfiles/.mcp.json` で自動読み込み）
- **Codex**: `~/dotfiles/coding-agents/codex/config.toml` の `enabled = false` を削除
- **Antigravity**:
  Antigravity CLI では `antigravity mcp enable inkdrop` による常時有効化は行わないこと（関係ない操作でも 1Password が立ち上がるのを防ぐため）。
  代わりに、一時的なスクリプト等を生成し、以下のように `run_shell_command` 経由で MCP サーバーの stdio に直接 JSON-RPC を流し込んで単発実行（Stateless Invocation）すること。
  例: `echo '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"search-notes","arguments":{"keyword":"book:inbox"}}}' | op run --env-file=~/dotfiles/coding-agents/inkdrop.op.env -- npx --prefer-offline -y @inkdropapp/mcp-server`

Stateless Invocation は1回あたり起動コスト（認証 + npm 解決）が大きいため、**MCP 呼び出し回数の最小化** と **並列化可能な呼び出しの同時実行** で起動コストを隠すこと。

## 入力

対象期間（任意）。例: `2026-04-28 〜 2026-05-04`

**省略時は「当月 + 前月」を走査し、未処理（`週次判定:` 行が無い）セクションを全部拾う**。ユーザーに期間を聞き返さない。

- 期間は正しさのためではなく**検索範囲を絞るためだけ**のもの。処理済みの印は `週次判定:` 行が持つので、同じ期間を2回処理しても二重に育てることはない。
- 既定を「先週1週間」にしない: **1週スキップするとその週が永久に取り残される**（ユーザーが覚えていない限り誰も拾わない）。2ヶ月ぶんを毎回なめれば、スキップした週も自動で回収される。
- 明示指定は残す（特定期間だけ処理したいとき用）。指定があればその期間だけに絞る。

## 前提

inbox-capture 時点で記事には3つの読了判定が付いている:

| 読了判定 | 日次の扱い | 週次の扱い |
|---|---|---|
| 即読了 | その場で読了済み | **対象外**（日次まとめに残すだけ） |
| 要約で十分 | 要約で完了 | **対象外**（日次まとめに残すだけ） |
| 後で読む | 深読み待ち | **本スキルの対象** |

「即読了」「要約で十分」のセクションは日次まとめノートに残ったままになる(検索で発掘可能)。古い日次まとめノート自体は月次/年次レビューで整理する。

**日次まとめからセクションを削除しない**（育てる・捨てるのどちらでも）。捨てた記事も後から検索で発掘できるようにするため、日次まとめは**その日に見たもの全部の完全なログ**として残す。週次で判断した結果は各セクションに `- 週次判定:` 行を追記して記録する:

```markdown
- 週次判定: 育てる → [ノートタイトル](inkdrop://note/xxxxx)
- 週次判定: 見送り（YYYY-MM-DD）
```

この行が**処理済みの印**を兼ねる（削除をやめた以上、代わりの印が要る）。抽出条件は「`読了判定: 後で読む` **かつ** `週次判定:` 行が無い」。

## 移動先ノートブック（育てる場合の bookId）

`create-note` / `update-note` の `bookId` には**実 ID** を渡す（`^(book:|trash$)` 必須。表示名 `tech/AI` では通らない）。2026-09-21 時点の実 ID:

```
book:_dtsK1wL    tech/web-engineering    # ソフトウェア工学・ウェブ技術全般
book:TnFNXDOy    tech/AI                 # AI開発手法・vibe-coding・harness-engineering
book:7beOT60T    tech/infra              # ネットワーク・DC・GPUクラスタ
book:Q3uI87J9    tech/cryptography       # 暗号
book:SvJkLqvg    tech/low-layer          # OS・ドライバ・コンパイラ・仮想化
book:5uqtSYb-    tech/neovim             # Neovim 関連
book:YPhSGe-q    others                  # その他
book:GkmAPwUu    someday-ideas           # 長期構想・未分解の興味
```

（親 `tech` は `book:PcBKYZbr`。直接の格納先には使わない）

ID が合わない・ノートブックが見つからないときは `list-notebooks` で引き直し、この一覧を更新する。

## 手順

Stateless MCP の起動コストを抑えるため、検索の絞り込みと並列 read-note を活用する。

1. **対象ノートを検索（絞り込み）**:
   - `list-notes(bookId: inbox)` で全件取得は禁止（inbox 肥大化時に重い）。必ず `search-notes` の `title:` 修飾子で月単位に絞る。
   - **期間省略時（既定）**: 当月と前月の2本を **並列で** 実行し、結果をマージする（日付での絞り込みはしない。未処理セクションを全部拾うため）。
     - `search-notes(keyword: 'book:inbox title:"inbox YYYY-MM"')` × 2（当月 / 前月）
   - **期間指定時**: 同月内なら 1 回、月をまたぐなら **月ごとに並列で** 実行し、取得後にタイトルの日付を解析して指定期間内のノートだけに絞る。
     - 月またぎ (例: 2026-04-28 〜 2026-05-04): `book:inbox title:"inbox 2026-04"` と `book:inbox title:"inbox 2026-05"` を並列に呼び、結果をマージ
2. **「後で読む」セクションを抽出**:
   - 対象ノートに対して `read-note` を **並列で** 実行する（読み込みなので競合しない）。
   - `読了判定: 後で読む` を含み、**かつ `週次判定:` 行がない**セクションだけリスト化する（前者は inbox-capture が、後者は本スキルが書き込むフィールド）。
3. **セクションごとに2択判定**（ユーザーに確認しながら進める）:
   - **育てる** → 個別ノート化フロー（下記）
   - **捨てる** → その場では何もしない（記録は手順4でまとめて行う）
4. **判定結果を日次まとめに追記**: セクションごとに `- 週次判定:` 行を足し、日次まとめ 1 ノートにつき `update-note` を **1回だけ** 呼ぶ（セクション単位で呼ばない）。**セクション本体は消さない**。
   - 育てる → `- 週次判定: 育てる → [ノートタイトル](inkdrop://note/xxxxx)`（`create-note` の戻り値の `_id` から `note:` を落としたもの）
   - 捨てる → `- 週次判定: 見送り（YYYY-MM-DD）`
5. **NotebookLM 昇格チェック**: タグ単位で3本以上溜まったものがあれば `notebooklm-judge` の実行を提案

## 「育てる」フロー

**週次セッション内で完結させる**。深読みを待つ中間状態を作らない（待ち状態を持つと、それを回収するトリガーが別途必要になり運用が複雑になる）。

1. AI: `create-note` を **1回だけ** 呼んで個別ノート化する。引数は `bookId`（「移動先ノートブック」から選ぶ）/ `tags`（サブテーマタグの tag ID。決め方は下記）/ `status: "active"` / `title` / `body`（日次まとめの該当セクション）。
   - **`create-note` は `bookId` と `tags` を同時に取れる**ので、作成 → 移動 → タグ付けを複数回の MCP 呼び出しに分けない
   - **タグとノートブックは日次の要約を見て決める**。深読みを待たない——サブテーマ粒度の分類（`harness-eng` か `pqc` か等）は要約で十分判断できる
   - **検索はタグ名、`tags` 引数は tag ID**（`search-notes(keyword: 'tag:xxx')` と `tags: ["tag:xxxxx"]` で指定方法が違う）。ID は `list-tags` で引く
2. AI: 手順4で日次まとめに `- 週次判定: 育てる → [リンク]` を追記する（セクション本体は残す）

### 深読みはユーザーの任意のタイミング

個別ノート化されたノートを、ユーザーが読みたいときに読み、考察をノートに書き足す。**書かなくても何も壊れない**（AI 側に待ちも回収もない）。深読みの結果タグ・ノートブックが違うと分かったら、その時点で直せばよい（ユーザー手動でも、AI に依頼してもよい）。

## タグについて

- タグは **NotebookLM 昇格の単位** = **サブテーマ粒度**（例: `tech/AI` 配下なら `harness-eng`, `vibe-coding`, `prompt-caching`）
- 1ノート = 1タグ
- タグ付けはこのスキル（育てる時）のみ。inbox-capture 時点では付けない
- **状態管理にタグを使わない**（「深読み待ち」等のマーカータグを作らない）。タグは NotebookLM 昇格の集計単位なので、状態が混ざると昇格判定が歪む

## タグの決め方

1. `list-tags` で既存タグ一覧を取得
2. 記事内容と**サブテーマ粒度**で最も合致する既存タグを選ぶ
3. 既存タグで対応できない場合のみ `create-tag` で新規作成:
   - 作成基準: 「今後も同テーマの記事が継続的に増える見込みがある」場合のみ
   - 一発ネタ・特定イベント限定の記事にはなるべく既存タグで対応する（タグの乱立防止）
   - 色はランダムに選ぶ: `red` / `orange` / `yellow` / `olive` / `green` / `teal` / `blue` / `violet` / `purple` / `pink` / `brown` / `grey` / `black`
- ノートブック単位（`tech/AI` 等）は NotebookLM トピックとしては大きすぎる

## タイムアウトとリトライ方針

- **MCP 呼び出し (Stateless = Antigravity)**: タイムアウト 60秒（`op run` 認証 + `npx` 起動を含む）。失敗時は1回だけリトライしてよい
- **MCP 呼び出し (Persistent = Claude / Codex)**: タイムアウト 30秒。失敗時は1回だけリトライしてよい

## 注意

- **日次まとめのセクションは消さない**。育てた場合も個別ノートへのリンクを残す（日次まとめは完全なログ、個別ノートは育てた記事の置き場、と役割が違う）
- 「育てる」の深読みはこのセッションでも後日でもよい。AI 側に待ち状態は無いので、読まなくても運用は詰まらない
- 1セッションで全件こなさなくてよい（未判定セクションは `週次判定:` 行が無いまま残り、次回そのまま抽出される）
- **`bookId` は実 ID**: `^(book:|trash$)` に一致する実 ID が必要で、表示名（`tech/AI` 等）では通らない。上の一覧が合わなければ `list-notebooks` で引き直す
- **ノートブックの新規作成は MCP では不可**（作成ツールが無い）。必要なら Inkdrop のローカル HTTP API を直接叩く: `POST {INKDROP_LOCAL_SERVER_URL}/books` に `{"name": "...", "parentBookId": "book:..."}` を Basic 認証付きで送る（認証情報は `op run --env-file=~/dotfiles/coding-agents/inkdrop.op.env` が供給。curl は deny 済みなので `python3` の `urllib` 等を使う）
