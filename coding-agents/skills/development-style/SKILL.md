# 開発スタイルとコード設計

## 基本哲学: テスト駆動

- **テストが開発を駆動する**: プロダクションコードは「失敗するテストを通すため」に書く。テストは後付け作業ではなく、**それ自身が仕様書**であり設計の駆動役。
- **テスト容易性 = 良い設計**: テストしにくいコードは設計が悪い兆候。テストしやすさを優先すると自然に疎結合・高凝集に向かう。
- **包括的なテストが安全網**: テストが揃っていれば恐れずにリファクタリングと改善を続けられる。

## 開発サイクル: Red → Green → Refactor

小さな変更でもこのサイクルを回す。コードを出すときは今どのフェーズかを明示する。**ループの実施規律（赤の確認手順・最小実装・やり直しの判定）は `test-driven-development` skill（vendored）に従う**。以下はサイクルの要点。

- **探索**: まず対象を理解する。既存コード・契約・テストの構造を把握してから着手。
- **Red（失敗するテストを書く）**: 実装前に、これから作る単一機能に対する具体的で失敗するテストを 1 つ書く。
- **Green（最小実装で通す）**: 失敗テストを通すための最小限のコードだけ書く。余分な機能や美しさはここでは追わない。
- **Refactor（設計を改善）**: 全テストが緑のまま内部構造を改善する（重複排除・命名の明確化・複雑ロジックの単純化、下記コード設計の充足）。
- **区切り**: サイクルが意味のあるまとまりで完結したら、ここがコミット候補だと提案する。ただし `git add` / commit / push を実行するのはユーザーが頼んだときだけ（自動コミットはしない）。push 前は code-review + security-review 必須。
- **KPI / カバレッジ目標が与えられたら、達成するまで試行する**。ただしテストの意味を保つ ── カバレッジ数値を埋めるだけのテストや、assertion の薄いテストで"達成"を偽装しない。
- **不明瞭な指示は質問して明確にする**。着手前に曖昧さを潰す（推測で進めて手戻りするより、1 回聞く）。

## テスト規律（テスト = 仕様）

- **テストは仕様から書く**。実装から導出しない。テスト名は「何ができるべきか」を語る（HOW ではなく WHAT）。
- **Red は実行して確認する**。テストは書くだけでは Red にならない。必ず実行し、「想定した理由で落ちる」ことを確認してから実装に入る（error で落ちるのは Red ではない。いきなり通ったら既存挙動をテストしているだけ）。
- **実装迎合テストの厳禁**。実装を先に書いてから、それに合わせたテストを書くのは禁止。テストより先に書いてしまった実装は破棄し、test-first でやり直す。
- **テストを実装に合わせて書き換えない**。テストが落ちたら直すのは**コード**。テストの変更が許されるのは仕様そのものが変わったときだけで、その場合は「これは仕様変更である」と明示してユーザーの合意を取ってから変更する。
- **過剰テストの抑制**。LLM はテストを書きすぎる。テストする seam（公開境界。振る舞いを観測できるインターフェース）を**書く前に合意**し、仕様を満たす必要最低限に絞る。1 テスト 1 振る舞い。内部実装の詳細（private メソッド・呼び出し回数・内部コラボレータの mock）はテストしない。
- **トートロジーテストの禁止**。期待値をコードと同じ方法で再計算するテスト（`expect(add(a,b)).toBe(a+b)` の類）は通って当然で何も検証しない。期待値は独立した情報源（仕様・既知の正解例・手計算）から与える。
- **保証範囲を必ず文書化する**。作成したテスト群について「**何を保証し、何を保証しないか**」を人間が読める形で残す。置き場所は plan-doc の「動作確認」セクション（日本語可）か、テストファイル冒頭のコメント（コードなので英語）。保証しない範囲を書くことで、カバレッジの錯覚と暗黙の信頼を防ぐ。

## 大規模・高クリティカル時のエスカレーション

- 実装に迎合しないテストが特に重要なモジュールでは、**test-writer を実装コードを見せない subagent に隔離**して要件・型定義だけからテストを書かせる（bias-free。判断基準は `parallelization` skill）。
- 常設の役割分離（test-writer / implementer / refactorer の 3-agent 構成）が割に合う規模（目安: 数万行級・高クリティカル）では、**プロジェクト側 `.claude/agents/` に定義**し、規律は本 skill と `test-driven-development` skill の preload で与える。custom agent は Claude Code 専用のためグローバル層には置かない。

## コード設計

- **関心の分離**（separation of concerns）を保つ。**状態とロジックを分離する**。
- **単一責任の原則（SRP）**: 1 つのモジュール / クラス / 関数は機能の一部分にだけ責任を持つ。
- **ガード節・早期リターン**: 深くネストした if-else を避け、早期リターンを使う。
- **可読性と保守性を最優先する**。命名は目的と意図が明確に伝わるようにする。
- **コントラクト層（API / 型）は厳密に定義し、実装層は再生成可能に保つ**。契約（インターフェース・型・スキーマ）を固定し、実装はそこから差し替え・再生成できる構造にする。
- **ハードコード禁止**: マジックナンバー・設定値（APIキー / URL / パス）・ユーザー向け文字列をロジックに直書きしない。意味のある定数・設定ファイル・環境変数に出す。
- **セキュリティ第一**: ユーザー入力は信頼しない。サニタイズと出力エンコードで XSS / SQLi 等を防ぐ。
- **静的検査できるルールはプロンプトに書かず、その環境の linter か ast-grep で表現する**。DRY・命名・マジックナンバー等、機械で強制できるものは散文の規約に頼らず機械に強制させる。
