# 開発スタイルとコード設計

全プロジェクト共通の進め方の詳細。CLAUDE.md「開発ポリシー」索引から必要時に読み込む詳細 doc（`@import` ではなく on-demand Read）。t-wada（和田卓人）の TDD の考え方を下敷きにする。

## 基本哲学: テスト駆動

- **テストが開発を駆動する**: プロダクションコードは「失敗するテストを通すため」に書く。テストは後付け作業ではなく、それ自身が仕様書であり設計の駆動役。
- **テスト容易性 = 良い設計**: テストしにくいコードは設計が悪い兆候。テストしやすさを優先すると自然に疎結合・高凝集に向かう。
- **包括的なテストが安全網**: テストが揃っていれば恐れずにリファクタリングと改善を続けられる。

## 開発サイクル: Red → Green → Refactor

小さな変更でもこのサイクルを回す。コードを出すときは今どのフェーズかを明示する。

- **探索**: まず対象を理解する。既存コード・契約・テストの構造を把握してから着手。
- **Red（失敗するテストを書く）**: 実装前に、これから作る単一機能に対する具体的で失敗するテストを 1 つ書く。対応実装がまだ無いので必ず失敗することを確認する。
- **Green（最小実装で通す）**: 失敗テストを通すための最小限のコードだけ書く。余分な機能や美しさはここでは追わない。
- **Refactor（設計を改善）**: 全テストが緑のまま内部構造を改善する（重複排除・命名の明確化・複雑ロジックの単純化、下記コード設計の充足）。プロセス全体でテストは緑を維持する。
- **区切り**: サイクルが意味のあるまとまりで完結したら、ここがコミット候補だと提案する。ただし `git add` / commit / push を実行するのはユーザーが頼んだときだけ（自動コミットはしない）。push 前は security レビュー必須。
- **KPI / カバレッジ目標が与えられたら、達成するまで試行する**。ただしテストの意味を保つ ── カバレッジ数値を埋めるだけのテストや、assertion の薄いテストで"達成"を偽装しない。
- **不明瞭な指示は質問して明確にする**。着手前に曖昧さを潰す（推測で進めて手戻りするより、1 回聞く）。

## コード設計

- **関心の分離**（separation of concerns）を保つ。**状態とロジックを分離する**。
- **単一責任の原則（SRP）**: 1 つのモジュール / クラス / 関数は機能の一部分にだけ責任を持つ。
- **ガード節・早期リターン**: 深くネストした if-else を避け、早期リターンを使う。
- **可読性と保守性を最優先する**。命名は目的と意図が明確に伝わるようにする。
- **コントラクト層（API / 型）は厳密に定義し、実装層は再生成可能に保つ**。契約（インターフェース・型・スキーマ）を固定し、実装はそこから差し替え・再生成できる構造にする。
- **ハードコード禁止**: マジックナンバー・設定値（APIキー / URL / パス）・ユーザー向け文字列をロジックに直書きしない。意味のある定数・設定ファイル・環境変数に出す。
- **セキュリティ第一**: ユーザー入力は信頼しない。サニタイズと出力エンコードで XSS / SQLi 等を防ぐ。
- **静的検査できるルールはプロンプトに書かず、その環境の linter か ast-grep で表現する**。DRY・命名・マジックナンバー等、機械で強制できるものは散文の規約に頼らず機械に強制させる。
